# Raspberry Pi Pico 2 W command surface and physical paths

Status: design inventory

This document separates commands implemented locally by the Pico, commands sent to the BMCU management
interface, and printer-protocol traffic generated by an optional printer stub. It is intentionally an inventory;
individual actuator commands require a separate safety contract before implementation.

## 1. Three command planes

```text
Bambuddy
   |
   | Wi-Fi: Pico-local API
   v
Pico 2 W
   |                         |
   | H1 management UART      | printer-side RS-485 stub
   | OWNER_USER              | OWNER_PRINTER
   v                         v
BMCU USART3              BMCU USART1/U7
```

| Plane | Purpose | BMCU owner | Normal production use |
| --- | --- | --- | --- |
| Pico-local | Configure and observe the bridge itself | none | yes |
| H1 management | Typed status, diagnostics, UI functions, approved service controls | `USER` | yes |
| Printer stub | Reproduce A1 mini protocol and timing for bench tests | `PRINTER` | no; isolated bench only |

The planes must not be confused. In particular, a USER command must not inject a fake printer packet into the
BMCU parser. A printer-stub test enters through the real printer-bus receive path.

## 2. Packed command selector

Commands represented inside the management/operation model use one byte:

```text
bits 7..6  owner
bits 5..4  trait
bits 3..0  opcode
```

### 2.1 Owner bits

| Bits | Owner | Source of truth |
| --- | --- | --- |
| `00` | `SYSTEM` | BMCU boot, timeout, recovery, and local state machine |
| `01` | `PRINTER` | USART1 traffic received through the printer-bus path |
| `10` | `USER` | USART3 traffic received through H1 from Pico |
| `11` | `SAFETY` | BMCU safety engine only |

Owner is derived from ingress, not trusted from the received byte. On H1, any command whose packed owner is
not USER is rejected. `BMCU_LOCAL` is represented as SYSTEM plus the original/root owner in operation logs.
No-owner state is internal metadata, not a two-bit wire value.

### 2.2 Trait bits

| Bits | Trait | Meaning |
| --- | --- | --- |
| `00` | `QUERY` | Small, cheap query; no state mutation |
| `01` | `DIAGNOSTIC` | Potentially multi-record or relatively expensive cached-state query |
| `10` | `UI` | Non-mechanical state/configuration change |
| `11` | `CONTROL` | Mechanical output, operation ownership, or safety gating involved |

Extraction is constant-time mask/shift logic:

```cpp
owner  = command >> 6;
trait  = (command >> 4) & 0x03;
opcode = command & 0x0F;
```

The 4-bit opcode gives 16 commands per owner/trait combination. Handler lookup may therefore use a
four-level trait switch and a 16-entry opcode table without string lookup.

## 3. Pico-local command types

These commands terminate on Pico and are exposed to Bambuddy. They are not forwarded as BMCU commands.

| Type | Examples | Notes |
| --- | --- | --- |
| Device administration | Pico version, device ID, uptime, reboot, network status | Reboot must report loss of BMCU monitoring |
| Link administration | UART state, last valid frame age, sequence gaps, reconnect | Must not toggle BMCU wiring or pins dynamically |
| Time/session | establish receive-time epoch, start session, identify boot | Pico/Bambuddy owns wall clock |
| Trace management | start/stop capture, filters, download/replay selection | Formatting and storage occur off BMCU |
| Stub-session control | arm, start scenario, stop, replay speed, expected outcome | Available only in explicit bench mode |
| Bambuddy bridge | publish optional-device state, capabilities, alarms | Normal production role |

Pico may autonomously maintain PING/PONG and request a resynchronization after a sequence gap. It must not
autonomously start mechanical USER operations merely because Bambuddy disconnected.

## 4. H1 management command types

H1 commands are transported by BMCU Link: COBS, CRC16, fixed integer fields, and 115200 8E1.

### 4.1 QUERY

Expected to complete with one small response and remain safe during printing.

| Command | Status | Result |
| --- | --- | --- |
| `PING` | implemented | PONG token and `hw_tick32` |
| `GET_STATUS` | implemented | 27-byte aggregate STATUS |
| `GET_DEVICE_INFO` | planned | firmware, protocol, capabilities, hardware identity |
| `GET_ACTIVE_OPERATION` | planned | current owner, phase, resources, operation ID |

### 4.2 DIAGNOSTIC

Read-only from the machine-control perspective. Responses may be split into bounded fixed records.

| Command | Status | Result |
| --- | --- | --- |
| `GET_FULL_STATUS` | specified | global, four channels, printer bus, counters |
| `GET_SENSOR_SNAPSHOT` | candidate | detailed cached sensor records |
| `GET_BUS_STATUS` | candidate | printer link state and parser/response counters |
| `GET_RECENT_EVENTS` | candidate | bounded binary event-ring drain |
| `GET_DIAGNOSTIC_COUNTERS` | candidate | full-width management and control counters |

Diagnostic requests must read cached values. They must not synchronously poll AS5600/ADC hardware or wait for
the printer bus. Only one multi-record snapshot is active at a time; another request receives `BUSY`.

### 4.3 UI

Changes presentation or observer configuration but never motor output, slot selection, or filament routing.

| Command | Status | Restrictions |
| --- | --- | --- |
| `SET_LED_MODE` | implemented | mandatory timeout; restores normal display |
| `SET_EVENT_FILTER` | candidate | changes only management telemetry filtering |
| `SET_TRACE_MODE` | candidate | bounded rate/duration; critical events cannot be filtered |
| `CLEAR_DIAGNOSTIC_COUNTERS` | candidate | result is logged; does not clear safety evidence |

UI commands may run alongside printer ownership because they use independent resources.

### 4.4 CONTROL

CONTROL is a future service interface. It is disabled by default and must use operation ID, TTL, preconditions,
resource ownership, result events, and a local BMCU timeout.

| Command family | Purpose | Minimum guard |
| --- | --- | --- |
| `REQUEST_LOCAL_STOP` | inhibit BMCU motor output | always safe to request; outcome still reported separately from printer pause |
| `TEST_MOTOR` | direction/PWM/duration bench pulse | bench enable, hard duration/PWM bounds, no printer ownership |
| `TEST_FEED_DISTANCE` | bounded feed/retract test | sensor validity, operation lease, jam timeout |
| `LOAD` / `UNLOAD` | exercise normal filament path | printer offline, valid slot, abort state machine |
| `SELECT_SLOT` | select a test channel | no active motion or printer operation |
| `ACK_SAFETY_LATCH` | record operator acknowledgement | must not automatically clear latch or resume |
| `RESET_CONTROL_ERROR` | request recovery evaluation | BMCU rechecks conditions before clearing |

The Pico/Bambuddy authorization decision does not replace BMCU validation. BMCU is the final authority for
motor limits, current state, resource conflict, and safe abort behavior.

## 5. Printer-stub command/traffic types

Printer-stub mode generates the existing A1 mini printer protocol rather than H1 USER CONTROL commands. It is
useful for end-to-end tests of the BMCU printer parser, decision logic, response construction, sensors, and motor
state machine.

| Traffic/scenario | Test purpose |
| --- | --- |
| Heartbeat and discovery | establish/lose printer-online state deterministically |
| Status and capability queries | validate reply type, length, state, and timing |
| Slot selection | exercise target/slot validation and state transitions |
| Feed/retract/load/unload | reproduce normal motor command sequences |
| Filament metadata | validate per-spool state without motor output |
| Runout and spool-swap sequence | reproduce the failure being investigated |
| Invalid target/length/CRC | verify ignore/reject reason and error counters |
| Recorded trace replay | compare known A1 traffic with BMCU decisions and H1 telemetry |
| Timing variation | delayed heartbeat, duplicate packet, burst, and timeout behavior |

The stub session should record expected reply, actual reply, printer transaction record, BMCU decision reason,
sensor snapshot, and final motor state under one scenario/operation ID.

## 6. Physical path memo

### 6.1 H1 management path

```text
Pico TX  -> H1-2 EXIT_RX -> PB11 / USART3_RX
Pico RX  <- H1-1 EXIT_TX <- PB10 / USART3_TX
Pico GND -- H1-4 GND
H1-3 3.3V: not connected when Pico is USB powered
```

- Electrical interface: 3.3 V TTL UART
- Runtime setting: 115200, 8E1
- Derived ingress owner: USER
- Intended role: normal monitoring and typed BMCU management commands

### 6.2 Printer path

```text
A1 mini or differential stub
    <-> printer-side RS-485 A/B
    <-> onboard U7 transceiver
    <-> PA9/PA10 / USART1
    <-> BMCU printer parser
```

- Electrical interface at the printer connector: differential RS-485
- Runtime setting in current firmware: 1,250,000, 8E1
- Derived ingress owner: PRINTER
- Intended role: real printer traffic or an isolated bench stub, never both simultaneously

The exact printer-connector A/B pin numbers are not assigned here; they must be taken from the board connector
definition/schematic before building a stub cable.

### 6.3 H2 header is not the preferred stub injection point

```text
H2-3 MCU_TX = PA9 / USART1_TX and U7 DI
H2-4 MCU_RX = PA10 / USART1_RX and U7 RO
H2-1 SWIO, H2-2 SWCLK = programming/debug
```

H2 exposes MCU-side UART nets used by the ROM flasher. U7 RO can also drive `MCU_RX`; directly driving H2-4
during normal runtime can therefore cause contention. A printer stub should use the printer-side differential
connector through a suitable RS-485 transceiver. Direct H2 injection is unsupported unless U7 is deliberately
isolated/disabled and the electrical consequences are separately verified.

## 7. Supported operating modes

| Mode | H1 | Printer bus | Mechanical USER CONTROL |
| --- | --- | --- | --- |
| Production monitor | Pico management | real A1 mini | disabled |
| Production diagnostics | Pico management | real A1 mini | stop request only, if explicitly enabled |
| Isolated BMCU bench | Pico management | printer stub | bounded tests allowed after arming |
| Trace replay | Pico management/logging | printer stub | normally disabled; replay drives behavior through PRINTER path |

Entering bench/stub mode must be explicit and visible in Bambuddy. The real printer must be physically absent
from the differential bus. Loss of the stub heartbeat or H1 control session must lead to a bounded BMCU-local
motor stop; safety must not depend on a Wi-Fi round trip.

## 8. Recommended implementation order

1. Pico common BMCU Link decoder, PING, GET_STATUS, and reconnect handling.
2. GET_FULL_STATUS assembly and atomic Bambuddy baseline installation.
3. Binary EVENT and printer-transaction display.
4. Pico-local trace capture and bounded diagnostic configuration.
5. Isolated RS-485 printer stub with heartbeat and non-mechanical queries.
6. Trace replay and invalid-frame/timing tests.
7. Bounded CONTROL test commands only after ownership, lease, and abort tests pass.
